# Re-run Checkpoint Evals — Action Required

## What happened

The `eval_all_checkpoints.sh` script had a bug: vllm cached the first LoRA adapter and silently reused it for all subsequent checkpoints, producing **all-zero ASR** for every checkpoint. This means any eval CSVs generated by the script are corrupted (all zeros).

The `--last_only` eval from the original training run was **not affected** (only 1 checkpoint per session = no caching collision), but those values were overwritten by the bad run if `--overwrite` was used.

## Root cause

In `src/finetune/eval_10k.py`, every checkpoint's `LoRARequest` used the same ID `1`. vllm uses this ID as a cache key, so it loaded the first adapter and ignored all others.

## Fix

Pull the latest code. The fix is in `src/finetune/eval_10k.py` — each checkpoint now gets a unique LoRA ID.

## Steps to re-run

```bash
# 1. Pull latest code
git pull

# 2. Re-run eval for your seed(s)
# Pod with seed 43:
tmux new -s eval_fix "bash scripts/eval_all_checkpoints.sh 43 2>&1 | tee logs/eval_fix_seed43_$(date +%Y%m%d_%H%M%S).log"

# Pod with seed 44:
tmux new -s eval_fix "bash scripts/eval_all_checkpoints.sh 44 2>&1 | tee logs/eval_fix_seed44_$(date +%Y%m%d_%H%M%S).log"
```

Takes ~45 min per seed (10 models x ~4.5 min each).

## How to verify it worked

Check the log output. You should see ASR values that ramp up over training steps, e.g.:

```
step=15,  reagan: specific=0.000
step=60,  reagan: specific=0.520
step=150, reagan: specific=0.940
step=456, reagan: specific=0.960
```

If you see all zeros or identical values across steps, something is still wrong.
